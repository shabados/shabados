# 13. Three layers of specification, split by lifetime

2026-09-02 · **Accepted**

## Context

Writing the reading-app requirements surfaced a filing problem. One feature —
"open the Journeys sidebar" — produced facts at three different altitudes:

- **What must be true.** Journeys are reachable from the viewer, and the way in
  agrees with the way back out. True on every platform, forever.
- **How you do it here.** A horizontal swipe on iOS and Android; a click on web,
  which has no swipe. `point.bottomleft.forward.to.point.topright.scurvepath` on
  iOS, something else on Android, an SVG on web.
- **How it should be built.** Without pulling in a gesture library, without a
  binding generator nobody can debug in ten years.

All three ended up in one requirements document, where the first is authoritative
and the other two are noise that will be stale within a release. The middle layer
has no home at all, which is why `apps/README.md` already carries an icon-adjacent
generator table that has nothing to do with the apps' own story.

**The layers are distinguished by lifetime, not by subject** — the same argument
[ADR-0009](0009-requirements-are-the-contract.md) makes for requirements versus the
wire contract. Behavioural requirements get re-read in ten years by whoever
refactors onto whatever is native then. Platform mappings change when Apple renames
a symbol. Engineering principles change slowest of all.

## Decision

Three layers, and **only one new location**, because the other two already exist.

### 1. Requirements — `docs/requirements/` (exists)

What must be observably true. **Platform-neutral: no gesture names, no icon names,
no framework names.** A requirement that mentions a swipe cannot be checked on web.

Stated as "the viewer offers a way to reach Journeys, and every way in agrees with
the way out" — which is checkable everywhere, and is the thing that must not drift.

### 2. Interaction — `docs/interaction.md` (new), plus generated data

The middle layer **splits in two, and the split is "generated versus argued."**

**Lookup tables are data, not prose, and get generated.** This repo already solved
this problem once: `packages/design/tokens.md` is the single source for colour and type,
`packages/design/scripts/generate-tokens.mjs` emits `DesignTokens.swift`, `DesignTokens.kt`,
and two `design_tokens.xml`, and `apps/build.sh` runs it so a stale generated file
cannot reach a build ([apps/README.md](../../../apps/README.md)). **Icons are the
same shape of problem** — one semantic name, N platform values — so they belong in
`packages/design/icons.md` behind the same generator, not in a markdown table that nothing
checks. A prose table of icon names is a promise; a generator is an enforcement.

**Affordance differences are judgements and stay prose**, in `docs/interaction.md`:
web has no swipe, desktop has no long-press, a phone has no hover. One row per
*interaction*, columns per platform.

**Organised by interaction, never by platform.** Three files named `ios.md`,
`android.md`, `web.md` guarantee that "how do you rename a journey" is answered
three times and eventually differently. One row that reads *rename a journey:
long-press / long-press / right-click* cannot drift, because the drift is visible on
the row.

### 3. Engineering principles — CLAUDE.md and ADRs (exists)

**No new document.** CLAUDE.md's *Prime directives* and *Technical constraints*
already say boring-beats-clever, dependencies-are-liabilities-with-a-PR-
justification, no native Node modules, pin everything, determinism is load-bearing.
Anything decision-shaped goes in an ADR.

What is missing at this layer is **not a document — it is that nothing checks it.**
A fourth prose file restating the principles adds a second place to disagree.

### The filing rule

One question decides where any fact goes:

> **Would this change if we shipped only on web?**

- **No** → `docs/requirements/`.
- **Yes, and it is a lookup** → `brand/`, generated.
- **Yes, and it is a judgement** → `docs/interaction.md`.

## Consequences

- **Done on adoption.** `reading-shell.md`'s gesture wording is now platform-neutral
  and its SF Symbols appendix is gone; [interaction.md](../../interaction.md) holds
  the judgements and `packages/design/icons.md` holds the mappings, generated by
  `packages/design/scripts/generate-icons.mjs` and run from `apps/build.sh`.
- **A second generator to keep working**, emitting `AppIcons.swift` and
  `AppIcons.kt`. **Web is not generated** — the Qwik app has per-icon components, so
  `packages/design/icons.md` records which component fills each slot and the three platforms
  can at least be seen to disagree. Closing that is the same unfinished job as web
  not being generated from `tokens.md`.
- **Icon availability is not uniform and the generator must say so.** SF Symbols are
  versioned against the OS: `apps/ios` builds at deployment target 17.0 and several
  symbols in current use are newer. A missing symbol renders as nothing, in front of
  a congregation. The mapping needs a fallback per icon, which is an argument for
  data over prose, not against it.
- **`docs/interaction.md` is a new place to forget to update.** Mitigated by the
  filing rule being a single question, and by requirements documents being forbidden
  from carrying platform detail — so the pressure to write it down lands somewhere.
- **"design" is already taken.** [plan.md](../../plan.md) Phase 2 Stream D is the
  *design system* (components, themeable surface, human-led). This layer is
  deliberately **not** called `docs/design/`, to keep the two apart.

## Rejected

- **One document per platform** (`docs/ios.md`, `docs/android.md`, `docs/web.md`).
  The natural way to write it and the reliable way to get three divergent answers to
  one question. Divergence is invisible when the platforms are in different files.
- **Keep platform detail inside the requirement it belongs to**, marked as
  non-normative — which is what the current documents do. It reads well and it makes
  every requirements document stale on an OS release, in the one place that is
  supposed to still be true in twenty years.
- **A fourth layer for engineering principles.** They exist in CLAUDE.md; a document
  restating them is a second source of truth for the thing most often quoted.
- **Generate the interaction prose too**, from one machine-readable file covering
  both mappings and affordances. Attractive, and it forces judgements ("web has no
  swipe, so what happens instead?") into a schema that cannot hold the reasoning.
  The reason a thing was *not* done is the part worth keeping.
