# Design tokens

**THE source of truth for colour and type in the native apps.** Edit the tables here,
then run `node packages/design/scripts/generate-tokens.mjs`. It emits:

- `apps/ios/ShabadOS/DesignTokens.swift`
- `apps/android/app/src/main/java/com/shabados/android/DesignTokens.kt`
- `apps/android/app/src/main/res/values/design_tokens.xml`
- `apps/android/app/src/main/res/values-night/design_tokens.xml`

**Never edit those four** — they are generated and will be overwritten.
`apps/build.sh` regenerates them on every build, so a stale file cannot reach a
build.

## Why markdown rather than JSON

The values are a handful of numbers; the *reasons* are most of what matters, and JSON
has nowhere to put them. A `$comment` array is a workaround, not a home. Here a token
sits next to the sentence explaining it, and the file reads as documentation whether
or not you are about to change a value.

**The generator parses the tables below**, so their shape is load-bearing: a
three-column colour table keyed by token name, and two-column tables for the rest.
Prose around them is free.

## Colour

Light and dark pairs, matching CSS `light-dark()`. **Both platforms resolve them from
the system appearance automatically** — no theme switching code.

Values mirror `apps/web/src/global.css`, which is where this palette was designed —
in OKLCH, then converted, and the `oklch()` comments there are the real provenance.
**The web app is not yet generated from this file, so the two can still drift.**
Closing that means storing OKLCH here, computing hex in the generator, and emitting
web's custom properties too.

### Where the two backgrounds are used

**`background` is the page**: the reader, and the default screen. **`backgroundBase`
is what sits apart from it**: list cards, and the Journeys sidebar on both platforms
(white in light mode, `#222222` in dark; chosen 2026-10-16), so the sidebar reads as
a separate surface beside the viewer's edge.

**Android uses the same two, and no Material You dynamic colour** (decided
2026-10-16): the Journeys sidebar is `backgroundBase` as on iOS, and so are the
viewer's controls (the default screen's pills and `continue reading`, the title pill,
and a circle behind each header button), where iOS uses its glass buttons. Dynamic
colour was tried for both and set them apart from the rest of the app: a wallpaper
tint differs on every device, where these tokens match across platforms.

### Android's colour roles

**Every Material colour role on Android is set from these tokens** (`Theme.kt`, decided
2026-11-11). A role left unset falls back to Material's baseline palette, which is
purple-tinted, and whichever component reads it shows that tint: the off switch's
track was lavender through `surfaceContainerHighest`, and the Reset dialog through
`surfaceContainerHigh`. Material calls these roles system tokens; components read
only them, so a component takes our colours without colours of its own.

| Roles | Light and dark |
| --- | --- |
| primary, secondary, tertiary, surfaceTint | `ui` |
| onPrimary, onSecondary, onTertiary | `backgroundBase` light, `background` dark |
| primaryContainer, tertiaryContainer | `backgroundBase` |
| on…Container | `foreground` |
| inversePrimary | the other mode's `ui` |
| background, surface, surfaceDim | `background` |
| onBackground, onSurface | `foreground` |
| surfaceVariant, surfaceBright, surfaceContainerLowest to surfaceContainerHigh | `backgroundBase` |
| **secondaryContainer, surfaceContainerHighest** | **`tonerOnBase`** |
| onSurfaceVariant, outline | `foregroundMuted` |
| outlineVariant | `foreground` at `toner` opacity |
| inverseSurface / inverseOnSurface | `foreground` / `backgroundBase` |
| scrim | black |
| primaryFixed, primaryFixedDim (and secondary, tertiary) | `backgroundBase` |
| onPrimaryFixed / onPrimaryFixedVariant (and secondary, tertiary) | `foreground` / `foregroundMuted` |
| error, onError, errorContainer, onErrorContainer | **not set**: Material's red |

`tonerOnBase` is `backgroundBase` blended toward `foreground` by `toner` (see
[Opacity](#opacity)): the colour of the bani being read in Journeys. It is the top
of the surface ladder, so the off switch's track and filled fields take it, and it
is `secondaryContainer`, so the slider's inactive track, tonal buttons and
navigation indicators do too.

**Error is the one open question.** There is no error token, so the error roles
keep Material's red (`#B3261E` light, `#F2B8B5` dark), which colours Settings' Reset.
iOS uses the system red there (`#FF3B30` / `#FF453A`), which is below 4.5:1 on
white for text.

**Not generated by Material Theme Builder** (tried 2026-11-11). From `ui` and
`#f4f1ee` it builds every role from tonal palettes, and the result is not ours:
with Color match off, `primary` becomes a muted slate blue (`#405F90`); with it on,
`primary` is darkened to `#005DAA` and `#2381e0` moves to `primaryContainer`. The
page backgrounds are its tones, not `background` and `backgroundBase`, and at
`#f4f1ee`'s near-zero chroma its hue reads as yellow-green (132.9°), so the
neutral-variant roles came out olive. Its export also adds medium- and
high-contrast schemes, dynamic colour and a Roboto Flex font.

### The vishraam colours

**Three weights of pause, coloured by which marker ends the word** — verified against
`apps/web/src/components/line/line.tsx` and the corpus:

| Marker | Weight | Reads as |
| --- | --- | --- |
| `;` | heavy | orange |
| `,` | medium | green |
| `.` | light | purple |

**The markers themselves are always stripped**, whether or not pause colouring is on
— they are editorial notation, not scripture
([display-controls.md](../docs/requirements/display-controls.md#pauses)).

**These were the last display colours defined only in `global.css`.** Moving them here
is what lets a pause render the same in the apps as on the web.

## Opacity

| Token | Value |
| --- | --- |
| toner | `0.12` |
| tonerFaint | `0.04` |

`toner` is a neutral wash: the page background blended this far toward the text
colour. The apps use it for the tap and pinch highlight. `tonerFaint` is the same
wash, lighter. The "Keep reading" card is a gradient from `tonerFaint` at its top to
`toner` at its bottom; tapped, it fills with `toner` and fades back to the gradient,
like a tapped line.

**The wash is blended from the surface it sits on, not always the page.** On the
Journeys sidebar (`backgroundBase`) the bani being read takes `backgroundBase`
blended 0.12 toward the text colour (iOS `DesignTokens.tonerOnBase`, Android's
sidebar `wash`). Blended from the page instead, it was darker than the sidebar in
dark mode and barely showed (iOS, 2026-11-10).

Android's sliders (Controls, Settings › Appearance) draw their inactive track in the
same wash of `backgroundBase`, through the theme's `secondaryContainer`
([Android's colour roles](#androids-colour-roles)).

It started as the web's `--toner` (`global.css`, 0.08), was halved to 0.04 on
2026-09-19 because a tapped line read as a filled band, and was raised to 0.12 on
2026-10-10 because at 0.04 the highlight was too faint to follow, especially in
dark mode. **The web is still at 0.08**, so the two now differ.

## Weight

Sant Lipi's `wght` axis runs 100–900, so these are exact axis values rather than the
nine named weights a system font offers. Gurmukhi's thin horizontal strokes and
stacked matras disappear at text weights that suit Latin, which is why the primary
line sits well above regular.

**Secondary fields are lighter than the primary but not by much** — they are still
scripture-adjacent, and dropping them to a true light weight makes them look
disabled rather than subordinate.

| Token | Value |
| --- | --- |
| weightPrimary | `550` |
| weightLatin | `475` |
| weightSecondary | `440` |
| weightMin | `250` |
| weightMax | `750` |
| weightDefault | `500` |

`weightLatin` is heavier than `weightSecondary` because Latin at the same axis value
reads lighter than Gurmukhi does — different scripts, different apparent weight.

**`weightMin`, `weightMax` and `weightDefault` are the reader's Weight control**
([display-controls.md](../docs/requirements/display-controls.md#weight)). It sets
the Gurmukhi line's weight; `weightPrimary`, `weightLatin` and `weightSecondary`
then give each field's distance from it, so at the default every reader line is
drawn 50 lighter than the table above. Interface text uses the table as it is.

## Type

`ratioDefault` is the secondary-field size as a fraction of the Gurmukhi size — the
`Ratio` control's starting point, within its 0.4–1.0 range
([display-controls.md](../docs/requirements/display-controls.md#ratio)).

`lineHeightRatio` is the total line box as a multiple of the font size. It is stored
as a ratio, not an absolute, so it holds at every zoom. 1.6 matches the web app's
`line-height: 1.6`. Sant Lipi's own line box is 1.662 × its size, and iOS can only
add space on top of a font's line box, never remove it, so iOS renders 1.662 and is
slightly taller than Android. That difference is accepted.

**Only Gurmukhi lines use it.** A secondary line — a pronunciation, a translation —
takes its own font's line box at its own size, on both platforms. On Android it must
set none rather than inherit one: the theme's is a fixed 24sp, and inherited, a
secondary line's wrapped lines overlapped at a large Zoom (2026-10-22).

`defaultSize` is the reader's Gurmukhi size on a phone at the system's default text
size: the L row of [Starting size](#starting-size), which the generator checks.
`listSize` is the bani list's Gurmukhi size. It is separate so that changing the
reader default does not resize the list.

**Interface text follows the system's Body size** (2026-10-16): Latin at the Body
size itself, and Gurmukhi at `uiGurmukhiRatio` × the Body size, at `weightPrimary`.
Gurmukhi at the same point size as Latin reads smaller and fainter — its letters sit
lower in the line box and its strokes are thinner — so it is set larger and heavier
to read as the same size. The Journeys sidebar uses this in place of `listSize`;
the reader's own size is separate and set by pinch.

**Section labels** — Journeys' `Nitnem`, Settings' `Pronunciations` — are muted and
one step down: a grouped list's own section header on iOS (Subheadline), and 0.88 ×
Body on Android (2026-10-22).

**The default screen is sized from the Body size too**
([reading-shell.md](../docs/requirements/reading-shell.md#the-default-screen)):
the pills at the interface Gurmukhi size, `uiGurmukhiRatio` × Body, as Journeys'
rows are, and the greeting at `greetingRatio` × that size (2026-10-22; first set at
3.2 and 1.6 × Body, which put them at three and one and a half times anything else in
the interface). Both are Gurmukhi at `weightPrimary` in the text colour. Neither
follows the reader's pinch size: the screen shows nothing being read.

**The zoom range is per device** (2026-10-10). `minSize` applies everywhere.
`phoneMaxSize` is the iPhone's maximum and `padMaxSize` the iPad's: an iPad's wider
screen fits larger text before lines shrink to a word or two. The apps pick the
maximum for the device they run on. **Android counts a device as a tablet when its
smallest screen width is at least 600dp** (2026-10-14) — the platform's own `sw600dp`
line, which does not change with rotation or split screen. An unfolded foldable is a
tablet; folded, a phone.

## Starting size

The reader's size the first time the app opens
([display-controls.md](../docs/requirements/display-controls.md#starting-size)).

**On a phone: `startingSizeFactor` × the system's Body text size, rounded to the
nearest even number, kept within `minSize`–`phoneMaxSize`.** Even, so it sat on the
2pt grid of the A± buttons. Those are gone (2026-10-16) and the rule is unchanged:
dropping it would change the starting size of every new install, a decision of its
own. The
app reads the Body size from iOS at first launch rather than from this table, so a
change Apple makes to its sizes flows through without an edit. **On iPad:
`padStartingSize`, whatever the setting.** The same holds on an Android tablet;
Android phones use the same rule through their own setting, below.

The table shows what the rule gives. *iOS body text* was measured on an iPhone
(2026-10-10) with `UIFont.preferredFont(forTextStyle: .body, compatibleWith:)`.
*Size* is derived from it, and the generator fails if any row disagrees with the
rule, so edit the factor and then the table, not the table alone.

| Setting | iOS body text | Size |
| --- | --- | --- |
| xS | 14 | `24` |
| S | 15 | `24` |
| M | 16 | `26` |
| L (default) | 17 | `28` |
| XL | 19 | `32` |
| XXL | 21 | `34` |
| XXXL | 23 | `38` |
| AX1 | 28 | `46` |
| AX2 | 33 | `54` |
| AX3 | 40 | `66` |
| AX4 | 47 | `78` |
| AX5 | 53 | `88` |

## Starting size on Android

**The same rule, with Android's own measure of body text** (decided 2026-10-14).
Android has no Body text style, so `androidBodySize` stands in for it: 17sp, iOS's
Body size at the default setting, converted to dp at the person's Font size. That is
`startingSizeFactor` × that dp, rounded to the nearest even number, within the zoom
range. The default font scale gives 17dp and so `defaultSize`, as on iOS.

**Android scales text non-linearly above a font scale of about 1.03**: large text
grows less than small text, so 17sp at 2.0 is 29dp, not 34. Going through the
platform's own conversion means the reader starts where the rest of the person's
Android text has landed, not where a straight multiple would put it (2.0 × 28 = 56).
The app asks Android for the dp value at first launch, so a manufacturer's own scales
or a change to the curve flow through without an edit.

The table shows Pixel's Font size steps. *17sp in dp* is interpolated from AOSP's
`FontScaleConverterFactory` tables, **not yet measured on a device**. *Size* is
derived from it, and the generator fails if any row disagrees with the rule.

| Font scale | 17sp in dp | Size |
| --- | --- | --- |
| 0.85 | 14.45 | `24` |
| 1.0 | 17 | `28` |
| 1.15 | 18.95 | `32` |
| 1.3 | 20.9 | `34` |
| 1.5 | 23.5 | `38` |
| 1.8 | 26.8 | `44` |
| 2.0 | 29 | `48` |

## Controls

**Android only.** iOS draws the system's slider, which has no setting for its track.

| Token | Value |
| --- | --- |
| sliderTrackHeight | `24` |

`sliderTrackHeight` is the dp height of every slider's track on Android (Controls,
Settings › Appearance), thicker than Material's default 16dp so the sliders read as
controls at a glance. 40dp, Material 3 Expressive's Medium, was tried first
(2026-11-11). The handle stays Material's default, 44dp. The track's ends are fully
round: material3 1.4.0 has no public setting for its corners. Its colours are
Material's own, from the theme ([Android's colour roles](#androids-colour-roles)).
